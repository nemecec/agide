# Agide

A personal macOS desktop tool for agentic coding: a task tree whose leaves are surfaces (Claude sessions, browser tabs, Slack threads), with an app-hosted MCP server so the agent can do what the UI can do, a layout that the user and agents edit, an inbox with tasks and reminders, and profiles that run side by side. Architecture and contracts: `../docs/decisions/0013-stage2-architecture-and-contracts.md`, `../docs/decisions/0023-milestone-2-architecture-and-contracts.md`, `../docs/decisions/0029-milestone-3-architecture-and-contracts.md`, `../docs/decisions/0038-milestone-4-architecture-and-contracts.md` and `../docs/decisions/0041-milestone-5-architecture-and-contracts.md`. What is built and verified: `../docs/decisions/0014-milestone-1-results.md`, `../docs/decisions/0024-milestone-2-results.md`, `../docs/decisions/0030-milestone-3-results.md`, `../docs/decisions/0039-milestone-4-results.md` and `../docs/decisions/0042-milestone-5-results.md`. The review ladder's design: `../docs/decisions/0040-review-ladder-design.md`. The visual design: `../docs/decisions/0035-visual-design-system.md`, built as recorded in `../docs/decisions/0036-restyle-results.md`.

## Requirements

- macOS, Node 22.12 or later, pnpm 11.
- The `claude` CLI for real sessions (not needed for the tests).

## Run

```sh
pnpm install      # also downloads the Electron binary and repairs node-pty's spawn-helper
pnpm dev          # Electron with the Vite dev server
pnpm build        # production build into out/
```

Environment variables of the app:

| Variable | Effect |
|---|---|
| `AGIDE_ROOT` | App root holding `profiles/` and `registry/`. Defaults to `<appData>/agide`. The real review ladder script sets it to a temporary root so it can change the profile's tier settings. |
| `AGIDE_PROFILE` | Profile to open when `--profile=<id>` is absent. Default: the profile focused last, else `default`. |
| `AGIDE_USER_DATA` | Data directory of one unnamed profile, without profiles and registry (used when `AGIDE_ROOT` is not set). |
| `AGIDE_HIDDEN=1` | The window is never shown. Used by the end-to-end tests. |
| `AGIDE_CLAUDE_BIN` | Path of the `claude` executable. Defaults to the usual install locations, then `PATH`. |
| `AGIDE_CLAUDE_ARGS` | JSON array of extra arguments for every `claude` launch, such as `["--model","haiku"]`. |
| `AGIDE_PERMISSION_MODE` | Test override of the permission mode of sessions that name none: `default`, `acceptEdits`, `plan` or `auto`. Without it a session starts in the profile's default mode, `auto` unless the profile settings say otherwise. `bypassPermissions` is accepted only per session, with a confirmation, inside a provider that limits files and the whole process's network. |
| `AGIDE_SESSION_CWD` | Working directory of sessions started from the tree. Defaults to `Agide/<folder id>` below the home directory, created with mode 0700. A directory inside the app root is refused. |
| `AGIDE_TASK_BASE` | Base directory of task starts (`worktrees/` and `sources/`). Defaults to `Agide` below the home directory. Used by the tests. |
| `AGIDE_SRT_BIN` | Path of the `srt` executable for the srt provider. Defaults to `srt` on `PATH`; the srt tests also look for the probe's install prefix and are marked unavailable without one. |
| `AGIDE_BROWSER_APPROVAL_TIMEOUT_MS` | How long a browser permission request waits for an answer. Default 115000. Used by the tests. |
| `AGIDE_SWARM_RUNTIME=fake` | Swarm agents run on the in-memory runtime without processes. Used by some tests; without it every agent and every reviewer is a `claude -p` stream-json process. |
| `AGIDE_E2E_COVERAGE_DIR` | Set by `pnpm coverage:e2e`: every launched app writes V8 coverage there. |

## Use

Right-click the tree to add folders and surfaces. "New Claude session" is offered inside a folder: it starts `claude` in a PTY and opens its terminal. Clicking a session leaf shows its terminal again; a session from an earlier run shows as exited with a Resume button. Every session gets the app MCP server through `--mcp-config`, a file with mode 0600 in the session's directory under `sessions/` (the bearer token is never a process argument). The app removes the file once the session has started (`SessionStart`) and writes it again on resume, and removes leftover session directories at start. The server is scoped to the session's folder, so the agent can change the tree below that folder. Its tool calls show the CLI's own permission prompt in the terminal when the mode or an ask rule asks.

## Permissions

"New Claude session" opens a dialog with the title, the working directory and the permission mode. The mode starts at the profile default (`auto` for a profile that never saved permission settings) and a session keeps it across resume. The profile settings panel, reached from the settings button of the title bar or the tree's background menu, holds the default mode with a sentence per mode, how each class of outward action is handled, the Bash sandbox with its host lists and the folder-trust setting. The setup pane of a new profile states what the default mode allows and that agents run as your user.

The network allowlist of the Permissions section is also the policy of a provider that limits the whole process: under srt it becomes the sandbox's allowed domains, next to the Anthropic hosts and loopback.

Every launch writes ask rules for outward-facing tools (GitHub writes, pushes, publishing, ssh, connector writes, unknown connector and MCP tools) into `--settings`, and replaces the app's `PreToolUse` hook with an inspector: `ELECTRON_RUN_AS_NODE=1 <app> inspect.js <gate file>`. The inspector splits a Bash command into its simple commands (compound commands, subshells, substitutions, quoting, variables, `sh -c`, wrappers such as `env` and `sudo`, git options such as `-C`), classes each one and answers `deny` or `ask` with the class named, or no decision so that the mode decides. It never answers `allow`. A command it cannot read is asked about, and so are shell forms that hide the program (`env -S`, git aliases, a dynamic `gh api graphql` query). Under bypass mode an ask becomes a deny, so bypass is refused when the inspector cannot run (a missing `inspect.js`, or the container provider, whose capability statement says that only the ask rules apply there). The inspector starts in about 70 ms per call. The inspector writes the payload with its decision into the session's inbox directory; a denial becomes an inbox item (`gate:deny`), an approval card names the class, and a sandbox block becomes a status item. `node --experimental-strip-types scripts/real-claude-gate.mjs` runs the real CLI against the gate after `pnpm build`.

The launch settings deny the CLI's Read and Edit tools on the app root; a shell command run by the agent is not covered, because local sessions run as the user.

A new working directory makes `claude` ask whether you trust the folder, with "No, exit" selected. The app watches the terminal for that question. With "Answer Claude's folder-trust question for folders the app creates" on (off by default), it answers Yes for a directory it created in that task start, after reading the latest screen. Otherwise, and for any directory you picked, it shows a banner above the terminal and an inbox item, and you answer in the terminal. Each Yes adds an entry to the login's `.claude.json`.

The session's mode is the mode it launched with; the app does not follow a Shift+Tab switch inside the terminal, because the hook payloads that report it lie in a directory the agent can write. Refusing a permission dialog with Escape interrupts the turn and fires no hook, so the session shows as waiting and its approval item stays open until the next hook.

## Profiles

Unless `AGIDE_USER_DATA` is set without `AGIDE_ROOT`, each profile runs as its own process with its own data directory, browser partitions and Claude configuration directory. The first start moves the milestone 1 data into the `default` profile and keeps its Claude login. Start a profile with `--profile=<id>`; a second start of a running profile focuses its window.

The title bar shows the profile's tile, name and a 2 px bottom border in the profile colour, with the layout switcher, the usage meter, the inbox and the settings button; the tile opens the setup card of a new profile. The rail at the left edge lists the profiles with their colour and unread count; a click opens or focuses the profile. "New profile" creates one with its own Claude directory and isolated tool credentials (gh, git, ssh, AWS, npm and Docker locations inside the profile, and only an allow list of inherited environment variables). The setup pane of a new profile opens a terminal in an empty `Agide/login-<profile id>` directory below the home directory (outside the app root, where sessions are refused) to sign in to Claude, checks the login with `claude auth status`, and asks for the git identity. Plain `ssh` and `scp` run by an agent still read your default keys; only git uses the profile's ssh config.

A profile reads of the other profiles only their definition (id, name, colour, creation time) and their entry in `registry/` in the app root: the profile id, the process id, a random id per start, the time of the last refresh and the unread count.

## Inbox, tasks and reminders

The inbox tab lists items that wait for you: approvals and idle prompts from Claude hooks, failed turns, posts from agents (`inbox_post`) and fired reminders. An approval item appears when a session asks for permission, notifies only when the dialog is still open after the CLI's own delay, and clears when the tool call runs. The detail card shows the project and session context and can peek at the session's terminal without focusing it. Agent text is shown as plain text. Unread items of normal or high urgency count towards the dock badge and the rail.

Agents use `inbox_post`, `inbox_list`, `inbox_resolve`, `task_create`, `task_list`, `task_update`, `reminder_create`, `reminder_list` and `reminder_delete`. Reminders take an RFC 5545 RRULE subset in a time zone; a rule above 48 occurrences a day is refused. Reminders missed while the app was closed fire at the next start: by default one item for the latest missed occurrence (`catchUp` `latest`), or one per occurrence (`each`), or none (`none`).

## Browser tabs and observation

"New Browser tab" in a folder adds a `browser-tab` leaf. Its tab chrome (back, forward, reload or stop, the address field with the host emphasised, the service badge, the observation control, Open in Chrome and a menu with copy URL, clear site data and DevTools) is drawn by the app above the page view, so a page cannot draw over the address or over a permission request. Only `http`, `https` and `about:blank` load; typed text that is not an address is refused, never searched. Each service (`jira`, `github`, `notion`, `slack`, `discord`, `web`) has its own persistent partition under the profile's data directory, and a link to another service opens a tab of that service next to the source. Pages get no permissions except fullscreen and sanitized clipboard writes.

Every session also gets the `agide-browser` MCP server (`/mcp/<session>/browser`), with the Claude in Chrome tool names: `tabs_context_mcp`, `tabs_create_mcp`, `tabs_close_mcp`, `navigate`, `computer`, `read_page`, `find`, `form_input`, `get_page_text`, `javascript_tool`, `read_console_messages`, `read_network_requests` and `browser_batch`. Sessions start with `--no-chrome`. The app server adds `surfaces_observe`, `surface_highlight` and `browser_open_in_chrome`. Every call checks the folder scope first and answers a tab of another folder like an unknown id; page content in a result starts with an "Untrusted page content" line.

Observation is a switch per tab (off, on demand, live) that only the user changes, from the tab chrome or the tree row indicator. Off refuses every page tool and `surfaces_observe`, lists the tab without URL or title, and draws a "not shared" mask in place of the tab in `ui_capture_window`. The capture tries a blank view again for up to 1.5 s and draws the "page not captured" placeholder when no painted frame arrives; its leaf id is listed in `unavailable` in the result. A hidden window can have no display surface for a view, and then the retry ends in the placeholder. A call is cut at the end of the 1.5 s, or after 0.5 s when it starts later than 1 s in, and no call starts after the 1.5 s, so a view takes 2 s at most. Only views the caller may see are captured, waited for and listed: a view of another folder, in a masked pane, with observation off or of a chat service is not captured, not waited for and not listed. Slack and Discord tabs start off and never give page content. Clicking or typing in a page as an agent is an acting call: loopback addresses in `web` tabs run, other `web` origins ask once per session, Jira, GitHub and Notion ask on every call and refuse `javascript_tool` unless enabled for the site, Slack and Discord refuse. An agent that navigates to an origin outside loopback asks first, unless the origin is `https` and its host is on the profile's network allowlist (Permissions section) and belongs to no signed-in service. An answer to a navigation never allows clicks, typing or scripts on that origin, and an acting call checks the origin again after its approval and refuses when the tab moved. `browser_open_in_chrome` asks before an agent runs it. An agent that calls `navigate` without a tab gets an empty tab of its own first. The question is a bar in the tab chrome and an approval item in the inbox that links to the tab; the item's card offers Deny and Allow once, dismissing it denies, and a request of a session that ends is denied. Under the srt provider, tabs an agent opened or drives load only loopback, allowlisted hosts of no signed-in service and origins the user let the agent open; other requests of the page are cancelled. Native views hide behind still images while a drag, a dialog, a context menu, the tab menu or the observation popover is open. The access log (`observation_log` in the profile database) keeps time, session, node, kind, origin, size and outcome, never content. A `UserPromptSubmit` hook prints a short digest of changed tabs from `digest.json` in the session directory. `browser-blocked.json` in the data directory lists origins and path prefixes that force observation off.

## Task start

"New task…" in the tree menus opens a dialog that takes a prompt, a GitHub pull request (URL or `owner/repo#n`) or a Jira key or URL, a repository path for pull requests, a base and the permission mode. `task_start` does the same for the UI and for agents. A start creates a folder, a Claude session leaf, a `task_starts` row and a task in the inbox's task list, and opens a browser tab for a pull request or Jira source.

- A pull request runs in a git worktree under `~/Agide/worktrees`, on branch `agide/pr-<n>` fetched as `pull/<n>/head` from the remote whose URL matches `owner/repo` (read with `git config`, so `insteadOf` rewrites do not hide it). An existing branch name gets a suffix; nothing is overwritten.
- The pull request's title, author, state, head branch, description and changed files go into `task-source.md` under `~/Agide/sources/<folder id>`, passed with `--add-dir`. The typed prompt holds no pull request text; it tells the agent to read that file as untrusted data. Repository guidance comes from `CLAUDE.md` at `<remote>/<base branch>`, never from the pull request head.
- A Jira source asks the agent to read the issue through the user's connector.
- When an agent calls `task_start`, the start stays in the agent's folder, cannot use a looser mode than the agent or bypass, may use only repositories you already used, and counts against the cap of app-started agents (`agents.maxConcurrentAppStarted`, default 4) together with swarm agents, starts in progress included; at the cap an inbox item says so.
- A start that fails removes the worktree, the branch it created and the source directory. Removing a task folder does not remove its worktree yet.

## Agents and usage

Subagents of a session appear as rows under its leaf with their state (running, waiting, failed, done); the session leaf shows the running count, a waiting marker and a tally of agents that finished recently. Finished rows leave after a delay (done 10 s, failed 300 s by default; "Show finished agents" brings them back). The history pane (`agide/agent-history`) lists finished agents; the transcript viewer (`agide/transcript-viewer`) opens a transcript read-only, only after `realpath` shows it below the session's projects directory or the profile's transcript copies, which keep finished transcripts gzip-compressed under a size cap.

Every launch sets a status line command that writes `status.snapshot` in the session's events directory; only identifiers and numbers are kept. The usage pane (`agide/usage-ranking`) ranks sessions by recent cost per minute with heat markers and folder rollups; the usage meter in the title bar shows the own profile's plan usage, with every window and the forecast in its tooltip. Usage alerts (cost per minute, plan thresholds, a window that runs out) become inbox items whose Pause (Esc in the terminal) and Stop act only on a click. Costs computed from tokens use `src/core/usage/prices.json` and are labelled as estimates. Settings live in the profile's `agents` key and are changed with `agents_settings_set`. Swarm agents are app-started agents on the `-p` stream-json path: each has a row with origin `app-started`, its cost is the one the CLI reports in its results, and its token usage feeds the ranking.

## Swarms

"New swarm…" in the tree menus opens a dialog with a Form and a JSON tab for a swarm definition (0037, 0038); `swarm_start` does the same for the UI and for agents (an agent's call asks the user first, through the `app.agent_start` ask rule). A swarm gets a folder, and each agent a `claude -p` stream-json process started through the profile's isolation provider and a leaf in that folder with its run state. The folder holding swarms shows how many swarm agents run against the cap (`agents.maxConcurrentAppStarted`, default 4). Live sessions that agents started with `task_start` count against the same cap; swarm agents beyond it wait in a queue (oldest swarm first, then stage, then definition order), and a `task_start` at the cap is refused. An agent queued for longer than 5 minutes raises an inbox alert.

A definition names the goal, the repository and base, the permission mode (auto by default; the dialog offers no bypass), the highest tier, the failure policy (`stop-dependents` by default, `continue` or `stop-swarm`), the budget (total, per agent, turns per message, wall clock, review share) and the agents, each with a role, a tier (`strong`, `mid`, `small`), a workspace (`worktree`, `readonly` or `scratch`), a stage or `dependsOn`, the paths it owns, its tools and connectors, whether it may start swarms, and a prompt. Each agent's mode is the strictest of its own, the swarm's and the caller's. The budget is reserved per agent and passed as `--max-budget-usd`; the app also stops an agent at its reservation and the swarm at its total or wall clock, from the cost the CLI reports and token estimates between results. Agents of a later stage get the results of earlier agents in an `inputs.md` file as untrusted data, never in their prompt.

A tool call that needs permission becomes an inbox approval item that only the user answers, with Allow or Deny on the card, which shows the tool input in full; an unanswered call is denied after the approval timeout. The swarm pane (`agide/swarm`) shows the agents, the budget meter, the results and Pause, Resume (for a paused swarm) and Stop; a stopped swarm continues when you send a message to one of its agents. Agents use `swarm_start`, `swarm_list`, `swarm_status`, `swarm_send`, `swarm_interrupt`, `swarm_stop` and `swarm_results`; a session sees the swarms in its folder scope and steers only the swarms it started, and an agent of a swarm the user started cannot start a swarm with the default spawn depth. A swarm cannot be removed from the UI yet, and its worktrees and scratch directories stay until then.

Settings in the `swarm` key of the profile's `settings.json` (no settings panel or command changes them yet):

| Key | Default | Effect |
|---|---|---|
| `tiers` | `strong` `fable`/`high`, `mid` `sonnet`/`medium`, `small` `haiku`/`low` | the `--model` and `--effort` of each tier; a row given here replaces the default row |
| `approvalTimeoutMinutes` | 60 (1 to 1440) | an open approval is denied after this time |
| `interruptedKeepSeconds` | 300 (0 to 3600) | how long an interrupted agent's process stays alive before it ends |
| `maxSpawnDepth` | 1 (0 to 2) | how deep agents may start swarms; at 1, agents of a swarm cannot start one |
| `maxActivePerSession` | 2 (1 to 8) | running or paused swarms per calling session |

The cap itself is `agents.maxConcurrentAppStarted` (1 to 16), changed with `agents_settings_set`.

Git worktrees of agents go to `~/Agide/worktrees`, scratch and inputs directories to `~/Agide/swarms/<swarm id>` (below `AGIDE_TASK_BASE` when set), outside the app root, where every launch denies the CLI's Read and Edit tools. Stored patches stay in the profile's data directory.

## Review

Work of swarm agents with a `worktree` workspace is reviewed before it can be merged (R19, 0040 to 0042). When such an agent's run ends, the app captures its worktree as a changeset, runs the project check, adds the rule reasons and sets a rung: A (the app accepts after a passed check), B (a reviewer agent may accept), C (you read the summary), D (you read the hunks that reasons and findings point to) or E (you read every hunk). A reviewer agent runs at B and before C to E. A changeset that needs you becomes a review item in the inbox.

The review pane (`agide/review`) opens from "Review work" in the menu of a swarm folder or a worktree agent, from the Review tab of the swarm pane and from Open on a review item. It lists the latest changeset of each agent and the earlier ones, with the merge control. A changeset shows its state, its rung with every reason (source, evidence, hard floor), the check with its output tail, the reviewer's report with its author, the agent's claim marked as not verified, and its files with their seen state. The file and hunk views number the lines, show findings under their line and give each line a comment box; `j` and `k` move between hunks, `n` jumps to the next unseen hunk and `m` marks the focused hunk seen. A summary or hunk counts as seen after it stays in view in a focused window for the dwell time (1.5 s) or with "Mark seen"; marks bind to content hashes, so a hunk the agent changes must be read again. The action bar accepts (at D and E only when the required hunks are seen; at C and above without a report only with "Accept without the reviewer"), rejects with a reason, sends back the draft line comments and a message as one batch, raises the rung, or lowers it with a reason of at least ten characters, and below a hard floor only after a second confirmation. The inbox card offers Open, Accept and Send back up to rung C when no finding is `major` or above, Reject with a reason, and Raise budget for work that waits for budget. A repository alert (the repository changed outside the worktrees during a swarm, which closes the merge gate) offers "Accept the change" for the exact change it shows, and Open swarm. Agent and reviewer text is shown as plain text with control, bidirectional and zero-width characters escaped.

### Review policy

A project sets its review in `.agide/review-policy.json`, read from the base commit of the swarm, never from a worktree; an agent's edit of the file is a hard-floor reason. Without the file the built-in defaults apply and there is no check command. The JSON schema is `reviewPolicySchema` in `src/core/review/policy/schema.ts`; every key except `version` is optional:

```json
{
  "version": 1,
  "check": { "setup": ["pnpm", "install", "--offline"], "command": ["pnpm", "test"], "timeoutSeconds": 600, "network": "none", "env": [] },
  "retryLimit": 2,
  "paths": { "sensitive": ["infra/**"], "migrations": ["**/migrations/**"], "testConfig": [], "build": [], "generated": [] },
  "thresholds": { "small": { "lines": 150, "files": 8 }, "large": { "lines": 600, "files": 25 } },
  "rungs": { "deps.changed": "C" },
  "reviewer": { "tier": "strong", "effortB": "high", "effortHuman": "xhigh", "timeoutMinutes": 15, "usdPerRun": 2 }
}
```

`check.command` is an argument list without a shell (write `["sh", "-c", "..."]` for one). The check runs in a fresh checkout of the changeset and never with more power than the agent had: under `srt` with writes limited to the checkout, its own temporary directory and a directory of clones of the caches the run needs (each run, the checkpoint run and the base run alike, clones the cache subtrees of its tools, such as the Gradle module cache, the Maven repository, the Cargo registry cache, the npm cache and the pnpm store, and points the tools at the clones; the directory is removed when the run ends; the home directory stays the real one and read-only, so toolchains below it are found) for a profile with the Bash sandbox on or the `srt` provider (`not_run` when `srt` is not installed or a clone cannot be made), as a plain process only for a profile without the sandbox, and not at all (`not_run`) under `container`. Every run carries `AGIDE_CHECK_RUN=<run id>` and `AGIDE_CHECK_OWNER=<app pid>` in its environment, and the app, outside the sandbox, ends the processes of a run when the run ends (also one that called `setsid` and left the process group) and the processes of earlier runs when a run starts: it finds them by that marker and, for a process whose image is a system program that hides its environment from `ps`, by a working directory inside the run's checkout or clone directory, reads the marker again right before each kill and records the program names in the check log. A base run that left processes behind or found processes of an earlier run at its start ends `not_run`, and so does a run whose process list cannot be read. The check on the base commit must be green. The app runs it on the base commit first, once for each base commit and policy hash of a swarm, and reuses a green result for later changesets; a red result is run again with the next capture. A failed check on a green base is `check.failed` (rung C, sent back first). A failed check on a red base is `check.base_red` (rung C, not sent back): the card says that the check fails on the base commit as well, so it cannot tell good changes from bad, and you decide; a check that passes on a red base shows that the change made it green. A red base never lowers a rung, and it posts one alert in the inbox for the swarm, base commit and policy (not again after a dismissal or a restart; an alert that the app ended because nothing stands on its base any more is posted again when the base is in use again). A green base run of that base commit and policy resolves it, and so does the end of the last undecided changeset on that base, since bases are per agent after a merge: fix the base, or change `check.command` in the policy. A failure whose output shows only a word that tests print too (a refused connection, a 403, `Unauthorized`, `Forbidden`, a name that does not resolve) stays a failure and is sent back unless the base run fails with the same word, which ends both runs `not_run`; a missing program (also a missing JDK) or a sandbox denial ends the run `not_run` at once, and the end of the output holds the matched line (the reason names the problem and nothing of the output). The process sweep is hygiene and no security boundary, since a process that clears its environment and changes its directory is not found; at most it makes a base run red, which has rung C and one alert. A cache that holds another volume below its root is not cloned (`not_run`). The check cannot read the app root (the data, tools and Claude directories of every profile and the registry), the Claude directory of the default login (`~/.claude`, `~/.claude.json`), the logs and crash dumps, or the credential locations of the home directory. The check environment carries no credential of the user: the proxy credentials that `srt` adds (`CLOUDSDK_PROXY_USERNAME`, `CLOUDSDK_PROXY_PASSWORD`, `HTTP_PROXY` with user information) only authenticate to the run's own local proxy and are random for each run, and these names are dropped, whatever `check.env` lists (the log of the run says which): names that equal or end in `TOKEN`, `PASSWORD`, `PASSWD`, `PASSPHRASE`, `SECRET`, `APIKEY`, `_KEY`, `HEADER`, `JWT` or `_PW`, names with `AUTH`, `AUTHORIZATION` or `OAUTH` as a whole word between underscores, names that contain `CREDENTIAL`, and the prefixes `CLAUDE_CODE`, `ANTHROPIC_`, `GH_`, `GITHUB_` and `AWS_` (compared without regard to case); `GIT_AUTHOR_NAME` and `GIT_AUTHOR_EMAIL` pass. A pass is the check command's own exit with status 0: `srt` exits 0 for a program that ends by SIGINT or SIGTERM, and Node reads a death by a signal it cannot name (SIGEMT on macOS) as exit 0, so every check, under `srt` and as a plain process, runs under a small launcher shell that handles the signals that end a process by default, starts the program as an external command (a shell builtin as the first word of the command never runs inside the launcher) and hands out the program's own status (128 plus the number for a signal); a check that signals itself, its group or its parent is `failed`, and a cleanup such as `trap 'kill 0' EXIT` reads as `failed` with status 143. The kernel takes an exit status modulo 256, so `exit 256` is a pass: a check command should end with 0 for success and 1 for failure (for example `cmd || exit 1`), and a runner that exits with the number of its failures has to clamp it. Under `srt` a check cannot bind or reach a loopback port unless a program of a command of the policy is a tool that asks for it (`gradle` or `gradlew`, for its lock socket, as the program or as the first word of a command of a `sh -c` script; a marker file in the checkout and a word among the arguments do not count); where one does, `srt` also admits every loopback TCP service of the host, which is the price of the lock socket (0040 section 6). `srt` and the programs that start it run outside the sandbox, so the app looks them up only on the absolute entries of its own PATH that lie outside the directories the check writes, gives the `srt` process that PATH and a working directory outside the checkout, and puts the PATH of the profile back for the program inside the sandbox: a relative or empty entry in the PATH of the profile, and a program such as `srt` or `bin/node` that a checkpoint commits, never runs outside the sandbox (0040 section 6, "Host-side start of `srt`"). When the review module starts it removes what a killed app left: the processes of its runs, the checkouts with their temporary directories, the `srt` settings files and the clone directories. `rungs` sets the rung of a reason id; a hard reason only rises. `outward` and `deployCommands` are read and reported with a warning on the swarm start; they are not applied to launches yet. A user-level overlay in the profile setting `review.policy` has the same fields and only tightens the project policy.

Settings in the `review` key of the profile's `settings.json`:

| Key | Default | Effect |
|---|---|---|
| `dailyBudgetUsd` | 5 | list-price equivalent of reviewer runs per local day, lowered by the policy's `reviewer.dailyBudgetUsd` |
| `maxConcurrentChecks` | 1 (1 to 8) | checks that run at once |
| `dwellMs` | 1500 (200 to 30000) | the dwell time of seen marks (the renderer uses the default for now) |
| `policy` | none | the user-level overlay |

Commands: `review_list` and `review_get` are UI commands and MCP tools; `review_request_escalation` is an MCP tool without a UI binding (the user raises a rung with `review_escalate`); `review_accept`, `review_reject`, `review_send_back`, `review_comment`, `review_escalate`, `review_demote`, `review_seen` and `review_accept_repo_change` are UI only, since agents never decide reviews. A reviewer session lists only `report_review`; a worktree agent lists `report_outcome` (its claim and an optional rung request for the next capture) and never `report_review`.

### Review manager

The review module (0040, 0041) keeps changesets, their files and hunks (with the diff text), reasons, checks, reviewer runs and reports, decisions, comments and seen marks in the `review` tables of the app database, so removing a worktree or a ref loses nothing the views need. `PersistentReviewManager` runs the pipeline from a capture (check, rules, reviewer) and every actor's actions under the transition table: the app accepts at rung A only, a reviewer at rung B only, an agent only raises a rung with `review_request_escalation` or `report_outcome`, and only the user accepts, rejects, sends back, comments, escalates, demotes and marks seen. A new capture of the same agent supersedes the previous changeset, so its accept and the seen marks of changed hunks lapse; marks of unchanged hunks carry over by hash. Demotions are read from their decision rows, so they hold after a restart.

At start the manager ends reviewer runs a quit or a crash cut short as `app-exit`, records interrupted checks as `not_run` and runs them again, repeats steps that had not finished and starts queued reviews. A review that waits for budget starts when a run ends, at local midnight and at start. The budget is the swarm's review pot (`usdTotal` times `reviewShare`, which defaults to 0.3 for a swarm with a `worktree` agent whose definition leaves it out; the Form tab of the start dialog still sends 0, which leaves every review waiting for budget) and the day's allowance (`review.dailyBudgetUsd`, lowered by the policy). Review items in the inbox follow the agent's newest changeset under the key `review:<swarm>:<agent>`; a decision resolves the item.

`swarm_merge` (UI and tool; the tool is under the `app.merge` approve class, which a profile cannot loosen) merges the latest accepted changeset of each worktree agent into a local branch, one squash commit each, only when every worktree agent ended, each latest changeset is accepted at its current rung on its current content, and no `repo.armed` or `repo.ref_moved` reason is open. The git steps read and write objects through the common directory with attributes from the empty tree, hooks off and every filter and merge driver the configuration names blanked, and move the branch by compare-and-swap, or by a fast-forward in the main checkout when it has the branch checked out and is clean; a branch checked out in a linked worktree is refused. Before the merge the repository is compared with the snapshot taken at swarm start, and a changed configuration, hooks directory, `info/attributes` or ref refuses it. While a merge runs, no decision on the swarm's changesets is taken and a new capture waits. It never pushes.

The review module connects the pipeline at start: before the first agent of a swarm with a repository and a worktree agent launches, the policy is read from the base commit and the repository snapshot is taken; when a worktree agent's run ends, its worktree is captured against the base (or the merged checkpoint) with a temporary index; the rules give the reasons; the check of the base policy runs in a fresh checkout and never with more power than the agent had: a profile with the Bash sandbox on, or the `srt` provider, runs it under `srt` with writes limited to the checkout, a temporary directory and the run's own cache clones, reads denied for the app's data, logs, crash dumps and the credential locations, and an environment built from a list of names; it ends `not_run` when `srt` is not installed, when a clone cannot be made, when its setup fails or when its output shows an environment problem (a missing program, dependencies that cannot be fetched, a sandbox denial), only a profile without the sandbox runs it as a plain process, and under `container` it is not connected and ends `not_run`; a rung B reviewer runs on the swarm runtime with the `reviewer` tool set in a read-only checkout under the task base and reports through `report_review`. Worktree agents get the `worker` tool set, which lists `report_outcome`. Recovery of open work starts once the pipeline is connected.

## Isolation providers

The Isolation section of the profile settings lists the providers with their check and what each limits:

- `local` (default): `claude` on the host as your user.
- `srt`: Anthropic's sandbox runtime, installed by you (`srt` on `PATH` or `AGIDE_SRT_BIN`; the app looks the name up on the absolute entries of its own PATH that are outside every directory an agent may write, and starts the absolute file; see "Host-side programs" below). The launch is `srt -s <settings> -- claude …` with settings generated per session: writes only to the workspace, the hook directory, the CLI's temporary directory and the Claude configuration (its settings, `CLAUDE.md`, commands, agents, skills, plugins and hooks denied); network only to the Anthropic hosts, loopback and the profile allowlist; `allowPty` for the terminal and `allowLocalBinding` for the app's MCP server, which opens every loopback port to the agent. The Keychain stays readable and `.claude.json` writable. Bypass mode is offered only here.
- `container`: Docker, one `docker run -it --rm --init` per launch with mounts at the same paths and the gh directory read-only. It is listed with its statement and cannot be chosen, because no real `claude` has run in it; it has no network policy and the inspector hook cannot run inside it.

`isolation_status` and `isolation_set_provider` are UI commands, not MCP tools, so an agent cannot choose its own isolation.

### Host-side programs

Everything the app starts on the host outside a sandbox goes through `src/core/isolation/hostTools.ts`, so that code an agent writes cannot decide which program the app runs with the rights of the user (0040 section 6, "Host-side programs", has the reasons, the audit of the spawn sites and the real-tool tests):

- System tools (`df`, `chmod`, `ps`, `lsof`, `cp`, `env`, `open`) are started by a fixed absolute path (`systemTool`) with a fixed environment, in `/var/empty`.
- `git`, `gh`, `docker`, `srt`, `node` and `claude` are searched on an explicit list: the absolute entries of the app's own PATH (never the profile's) that lie outside the directories an agent may write, then the system directories, Homebrew and the directory of Docker Desktop. Relative and empty PATH entries are dropped. The process gets that PATH, an environment built for it and an empty working directory; an agent session keeps the workspace as its directory. A candidate is used only when its real path (links resolved) and the script that its pnpm shim names lie outside those directories too, and a path through `/System/Volumes/Data` counts as the same path without that prefix. The process of `srt` gets an allow-list environment (`HOME`, `USER`, `LOGNAME`, `TMPDIR`, `LANG`, `LC_*`, `TERM` and the names `srt` reads or sets). Every other variable of the profile, its PATH, `NODE_OPTIONS`, `DYLD_*` and `PS4` among them, is in that environment under the prefix `AGIDE_INSIDE_`, which nothing on the host reads, and the launcher shell inside the sandbox exports it under its own name: no value of the profile is an argument of any process, since every local account can read arguments with `ps`. A name that is not a shell identifier (`BASH_FUNC_*`) or that bash keeps for itself (`SHELLOPTS`, `UID`, `SHLVL`) does not reach the program, and on macOS neither does a `DYLD_` name, which macOS removes when it starts a protected program; the log of a check names them, and for a session the log of the app does.
- The directories an agent may write are one registry (`AgentWritableRegistry` in `agentWritable.ts`, read by the host tools and added to by the `srt` and the `container` provider before a launch): the workspace, working directory and hook inbox of a launch (for a check its checkout, temporary directory and clones), the directory of the hook inboxes, the working directories of the sessions in the store when the profile uses `srt` or `container`, and of every session those providers ever launched (also outside the task base), the Claude directory of the container provider, the Claude configuration directory of the profile, `~/.claude` and `~/.claude.json` for every profile, the CLI temp directory, the `extraWritePaths` of the isolation options, the task base, and the paths `srt` makes writable by itself (`/tmp/claude`, `/private/tmp/claude`, `~/.npm/_logs`, `~/.claude/debug`). `buildSrtSettings` takes its `allowWrite` from the same function, so the two cannot differ. The registry keeps every directory it learns in the table `agent_writable_directories` of the profile database and never removes one, so a closed session, an `extraWritePaths` entry you removed, a moved `AGIDE_TASK_BASE` and a restart leave it excluded. In memory it keeps only the directories that no other one contains (a workspace below the task base adds nothing), and a lookup computes the real path of each once, so a program start stays fast as launches accumulate. A write that fails (a locked or full disk) keeps the directory excluded and is tried again later. The `local` provider records nothing: its agent writes with your rights anyway, and a session in your home directory would otherwise exclude every program below it. A session of `srt` or `container` in your home directory, or in a directory that holds your tools, is recorded; when such a directory holds the `srt`, `node` or `claude` that a launch needs, the provider status says so and names the directory and the command that forgets it. To take a directory out after you checked or emptied it, quit the app and run `sqlite3 '<profile data>/app.db' "DELETE FROM agent_writable_directories WHERE path = '<directory>'"`; the app has no command for it. An `srt` session cannot read the profile database; it can read the rest of the data directory. If the only copy of `srt`, `node`, `docker` or `claude` lies in one of these directories (for example a `~/.cargo/bin` that you listed in `extraWritePaths`), the session or the check does not start and says so with a fixed reason; install the program in a directory the agents cannot write.
- If the only copy of `srt` is a shim whose code lies in such a directory (the pnpm store listed in `extraWritePaths`), or a `node` beside the shim leads into one (beside the file as it is started and beside its real file, since older shims do not resolve their links), it is refused too. A refusal names the role and the base name of the program, never a configured path; an error of the system is named by its code, and its message goes to the log of the check. A command that an isolation provider builds is spawned only with an absolute file. `hostToolsGuard.test.ts` scans the sources (TypeScript and JavaScript) and fails when a file starts a program in another way, takes a spawner as a value, loads or re-exports `child_process`, evaluates code, changes the command that a spawn reads, or builds or passes on `HostTools` outside the wiring, and in the files that spawn `command.file` when the command is shadowed by an untyped parameter, assigned by bracket or taken under another name; it also flags `process.binding`, `process.execve`, `Module._load`, `node:vm` and a `Worker` with `eval`. It stops accidental spellings, not a deliberate one.

## Layouts

The window shows a layout: `layouts/<id>.json` in the data directory, or a shipped preset (`session`, `pair`). Both presets place the profile rail at the left edge, the task tree, the surface host and the inbox as a tab beside the surface. Editing the file while the app runs changes the window; an invalid file keeps the running layout, shows the errors and is not rewritten until it is valid again. `window-layout.json` names the layout of the window. Every change is a revision in the app database, and Undo applies the previous one as a new revision. Agents use `blocks_list`, `layout_get`, `layout_validate`, `layout_apply`, `layout_undo`, `layout_switch`, `ui_open_to_side` and `ui_capture_window`; an agent changes a layout only while the focused node lies in its folder, and its captures mask every pane except a placeholder and a surface host that shows a node of its folder: the tree, the inbox, the rail, the agent, usage and swarm panes, and a surface host bound outside the folder by context or by value, with its dock tab, and the unread badge of the title bar, which counts the inbox of every folder; a scoped capture fills a slot of fixed size where the badge sits, also when nothing is unread, through a style rule on the document root, so neither the count nor the presence of a badge shows and a badge that mounts during the capture is covered. The plan usage meter of the title bar shows account-level plan usage, not data of folders, and stays visible. The mask is read again after the capture has waited for the views and after the pixels are taken, and the result names the mask that was applied. `layout_apply` and `layout_undo` refuse a value binding that the change adds or changes on an input that names a node, when the value is not a node of the agent's folder; a binding the layout already holds is skipped only when the instance has the same type and an equal binding, and on a pane type that is not registered and on the placeholder every value binding counts as a node reference; values on other inputs of known types are not checked. The formats are in `../docs/blocks.md`.

## Themes

All colours, sizes and timings of the renderer are `--agide-*` CSS variables that the theme store in `src/renderer/theme/` writes to `:root` from the active theme (0035). The built-in themes are in `src/core/theme/builtin/`:

## Test

```sh
pnpm typecheck    # tsc over the Node side (core, main, preload, e2e) and the renderer
pnpm test         # Vitest unit tests of src/core, src/main, src/shared and the renderer logic (Node, jsdom for hooks and panes)
pnpm coverage     # the unit tests with V8 coverage; thresholds on src/core, src/core/review, src/core/swarm, src/main, src/main/modules, the review module, src/shared, src/renderer/ui, the swarm and review panes and the renderer logic files; report in coverage/
pnpm e2e          # builds, then launches the app hidden with Playwright
pnpm mutation     # breaks each security and cost decision once (folder scope, navigation schemes, inspector rules, redaction, observation switch, the swarm cap and queue, permission caps of children, spawn depth, budget stops, approval answers, swarm tool scope, worktree removal, the stream-json runtime, and the review ladder: policy read from the base commit only, hard floors, raise-only rungs, agents that never demote or accept, the report tool scope, hash-bound seen marks and accept lapse, the merge gate, budget exhaustion and secret detection) and fails when no unit test notices; `pnpm mutation <name fragment>` runs a subset, such as `pnpm mutation budget:`
pnpm coverage:e2e # builds with source maps, runs the end-to-end tests and prints the coverage of the renderer and the main process; report in coverage-e2e/
pnpm parity       # every UI-bound command is an MCP tool or states an exemption; writes ../docs/parity.md
pnpm blocks-docs  # writes ../docs/blocks.md from the manifest and layout schemas
pnpm check:colours # fails when a stylesheet or component of the renderer holds a colour literal outside the allowlist in scripts/colour-literal-allowlist.json (empty), or when an allowlisted file no longer holds one; not part of pnpm check
pnpm visual-check # walks the UI states on fake data in a fixed-size window and writes one PNG per state into a new temporary directory (after pnpm build; --hidden keeps windows off screen)
pnpm check        # typecheck, unit tests and end-to-end tests
```

The Electron entry points hold no decisions: which frames may call commands, the window open and navigation policy, the web preferences, the focus request and the `window.api` object come from small functions (`src/main/ipcPolicy.ts`, `src/main/windowPolicy.ts`, `src/main/focusRequest.ts`, `src/shared/rendererApi.ts`) that the unit tests cover, including the foreign-frame, subframe, other-origin and `window.open` cases. `src/main/ipc.ts` and `src/main/window.ts` are tested against a mocked `electron` module. Renderer tests that need the DOM start with `// @vitest-environment jsdom` and use `src/renderer/testing` (a fake `window.api` and a render helper). Panes that load an engine with a canvas (the terminal) are tested with the engine mocked.

`pnpm coverage:e2e` measures what the end-to-end tests reach: `page.coverage` for each window and `NODE_V8_COVERAGE` for the main process, mapped to `src` through source maps and merged by `monocart-coverage-reports`. It prints functions, branches and lines per area and is not a CI gate. `e2e/coverageHook.ts` is active only when `AGIDE_E2E_COVERAGE_DIR` is set. `--reuse` rebuilds the report from the raw data of the last run.

`pnpm visual-check` (`scripts/visual-check.mjs`, helpers in `scripts/lib/visual/`) launches the built app with Playwright on sample data: temporary data directories, a fake `claude`, the fake `gh` of the task tests and a local test page. Its phases (`empty`, `workspace`, `dialogs`, `agents`, `inbox`, `browser`, `profiles`, `errors`, `appearance`, `focus`, `theme`, `swarm`, `review`) set the window to a fixed content size and write `<state>.png` from `ui_capture_window`, plus `<state>.page.png` from the renderer where DOM layers sit over a browser view, and `focus-order.json` for the keyboard order. Several phases show their windows on screen; `--hidden` keeps all of them off screen. `--only <phase,phase>` runs a subset and `--out <directory>` changes the parent directory. Each run writes a new directory, so runs before and after a change can be compared. macOS `screencapture` is tried for visible windows and skipped after the first refusal, which is what happens when the terminal has no screen recording permission. The `theme` phase captures the session, a dialog and the inbox in System light and dark, under increased contrast and with a pink accent, through the appearance adapter's test hook. Hidden windows do not draw the traffic lights. It is not a gate; results are in `../docs/decisions/0031-on-screen-check-results.md` and `../docs/decisions/0036-restyle-results.md`.

`pnpm mutation` (`scripts/mutation-checks.mjs`) edits one source line at a time, runs the unit tests that guard it and restores the file afterwards, also on Ctrl-C. A mutation counts as killed only when a test fails; a suite that does not load does not count. A new security or cost decision gets an entry in the script's list. A mutation that cannot change behaviour is left out of the list; the stage sort of the swarm queue is one, because the stage gates dependencies first. The same holds for a check that another check already makes redundant, such as the changeset id of a demotion token next to its content hash.

The browser view placement (`src/main/browser/viewPlacement.ts`: bounds scaling, eviction, download attribution), the navigation guards (`guards.ts`), the inspector command (`src/core/permissions/inspectCommand.ts`) and the blocked-address file parser (`src/core/browser/blocked.ts`) are pure or take their inputs as arguments, so their negative cases run in Vitest. `src/main/browser/ElectronViews.ts` is tested against a mocked `electron` module with fake views, windows and sessions.

The swarm tests: `src/core/swarm/runtime` runs the runtime contract suite against the in-memory runtime and against `StreamAgentRuntime` over the fake CLI `src/core/swarm/fixtures/fake-claude-stream.mjs` (a step language in the user messages, such as `/text`, `/tool`, `/sleep`, `/fail`, `/exit`, `/write`); `src/core/swarm/manager` runs the manager contract suite against the in-memory and the persistent manager, with a manual clock for retries, alerts and timeouts; `src/core/swarm/workspace` runs git on temporary repositories, including a repository configuration with a filter driver and a forged git directory.
